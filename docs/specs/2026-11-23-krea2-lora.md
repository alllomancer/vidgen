# Krea 2 LoRAs (`vidgen lora add`, `--lora` on Krea photos and first frames)

Jira: N/A
Date: 2026-11-23
Status: Approved
Last reviewed: 2026-11-23

## Problem

Uploaded and trained LoRAs only work with the Wan 2.2 14B video models. A LoRA made for Krea 2
(e.g. `~/Movies/lora/kera2_Unlocked_V3.safetensors`, flattened `lora_unet_blocks_N_attn_wq/wk/wo/gate`
keys) is refused at upload ("doesn't look like a Wan LoRA"), so Krea 2 images (photos without a
person, first frames of no-avatar videos and story shots) can't be styled with one.

## Approach

A LoRA name gets a kind, `t2v` (Wan, as today) or `krea2`, decided by the file's header at upload.
The same `--lora NAME[:WEIGHT]` list then routes each LoRA by its kind: Wan LoRAs to Wan, Krea LoRAs
to the job's Krea 2 step. No new flag. First version: Krea photos and video/story first frames.

Feasibility: the pinned Krea venv (`diffusers==0.41.0`) already has `Krea2LoraLoaderMixin` on
`Krea2Pipeline`; its converter (`_convert_non_diffusers_krea2_lora_to_diffusers`) maps the original
`krea-ai/krea-2` names (reference trainer, ComfyUI, AI-Toolkit). It does NOT handle kohya/musubi-tuner's
flattened `lora_unet_blocks_N_attn_*` keys (corrected during the live check; see the update below), so
`krea_gen.kohya_to_reference` converts those first. Checked on the
render box 2026-11-23. Krea 2 Turbo transformer: 28 layers, 48 heads x 128 = 6144 wide.

## Design

### Upload

- **Client** (`vidgen.lora_upload`, used by both `lora add` and the dashboard): reads the local
  file's safetensors header and detects the kind with the same rules the server uses (no network;
  the Lambda bundle holds only handler.py, so the CLI keeps its own copy and a unit test runs both
  on the same headers to keep them in agreement). Krea files are single-file only; `--high/--low` with a Krea file is
  refused locally ("Krea 2 LoRAs are one file; use --file"). The detected kind goes into
  `POST /loras/{name}/uploads {files: "single", model: "krea2"}`.
- **Reserve** (`lora_uploads`): `model` is `t2v` (default) or `krea2`. For `krea2` the presigned PUT
  goes to `loras/<client>/<name>/v<N>/krea2.safetensors`. If the name already has a registered
  version of the other kind, 400: "'NAME' is a Wan LoRA; use another name for a Krea 2 LoRA" (or the
  reverse). One kind per name, so `--lora NAME` always means one model.
- **Register** (`register_lora_upload`): finds `krea2.safetensors` or the `t2v_*` files and runs the
  matching check. `_check_krea2_lora(header)`:
  - LoRA weights present (`LORA_KEY`, as for Wan);
  - no keys of other families (`OTHER_MODEL_KEYS`) and no Wan markers (`self_attn`, `cross_attn`,
    `ffn`), so a Wan file can't register as Krea;
  - Krea block layout: `blocks[._]N[._]` with `attn[._]?(wq|wk|wv|wo|qkv_proj|gate)` or `mlp`
    (main blocks and the text-fusion `txtfusion_layerwise_blocks_N` / `txtfusion_refiner_blocks_N`,
    which `Krea2Transformer2DModel` also has; the user's file targets both);
  - dtype F16/BF16/F32 (`LORA_DTYPES`);
  - a 6144-wide layer (`KREA2_DIM`), else "doesn't match Krea 2 (no 6144-wide layers)".
  - A Krea file sent as `t2v` (or the reverse) gets the specific message "this is a Krea 2 LoRA"
    / "this is a Wan LoRA" instead of the generic one.
- `lora.json` for Krea: `{"models": ["krea2"], "files": ["krea2.safetensors"], "single_file": true,
  "source": "upload", ...}`, otherwise as today.
- IAM: the API role may additionally PutObject `loras/*/krea2.safetensors`.

### Rendering

- `_resolve_loras` adds `model` (`t2v` | `krea2`) to each item and, for Krea, `key` (the one file)
  instead of `high_key`/`low_key`. Limits per kind: at most `MAX_RENDER_LORAS` (2) Wan and 2 Krea;
  weight `LORA_WEIGHT` (0-1.5); version/step pinning as today (Krea has no steps: a `step` is a 400).
- `create_job` splits the list: `params["loras"]` (Wan, unchanged) and `params["krea_loras"]`.
  - **photos** with `model: krea2`: `loras` accepted, Krea only; a Wan LoRA is a 400 ("Wan LoRA
    'x' is for video; Krea 2 photos take Krea 2 LoRAs"). Photos with `model: qwen`: any LoRA is a 400
    (as today, the edit model takes none).
  - **video**: Krea LoRAs need `image_model: krea2` (which already requires `avatar: none`); else 400
    "Krea 2 LoRA 'x' needs --image-model krea2 (a Krea first frame)".
  - **story**: Krea LoRAs need `image_model: krea2`; they apply to the first frames of shots without
    avatars. If the plan gives every shot an avatar they go unused (noted in the result).
  - **avatar**, **describe**, **write**, **lora_preview**: a Krea LoRA is a 400.
- CLI `--lora` on `photos`: added (today it exists on video/story only). Dashboard pickers list Krea
  LoRAs only where the job can use them.
- **Worker**: `prepare_krea_loras(params)` downloads `krea_loras` into `LORA_CACHE` like Wan files and
  returns `[{"path", "adapter", "weight", "trigger"}]`. `krea.generate(items, progress, loras=[])`
  writes them into request.json; trigger words go in front of each Krea prompt (like `with_triggers`).
  `krea_gen.load` calls `pipe.load_lora_weights(path, adapter_name=...)` per LoRA, then
  `pipe.set_adapters(names, adapter_weights=weights)`. A load error exits the generator with
  "LoRA ADAPTER could not be loaded: ..."; the job fails with that message. Each Krea run is a fresh
  process, so there is no adapter state to clean up between jobs.
- The content filter is unchanged: every image, with or without LoRAs, goes through it; flagged
  images are re-rolled once and dropped if flagged again; there is still no switch to skip it.
- Job records and results list each LoRA with its `model`; Krea stats get `loras` (adapter names).
- `vidgen lora list` / dashboard Learning list show the kind (`krea2` instead of `motion`/`uploaded`).
  `lora use NAME --version N` works for Krea (no `--step`); `lora preview` refuses a Krea LoRA.

## Acceptance Criteria

- When `vidgen lora add moody --file F` is given a valid Krea 2 LoRA file, the client shall reserve
  with `model: krea2`, upload to `loras/<client>/moody/v1/krea2.safetensors`, and registration shall
  write `lora.json` with `models: ["krea2"]`; `lora list` shall show `moody v1 krea2`.
- When `kera2_Unlocked_V3.safetensors` (768 tensors, `lora_unet_blocks_N_attn_*`, BF16/F32) is
  checked, `_check_krea2_lora` shall pass and `_check_wan_lora` shall fail with "this is a Krea 2 LoRA".
- If a Krea file has no 6144-wide layer, is not a LoRA, has Wan or other-family keys, or an unsupported
  dtype, then registration shall return 400 with that reason and the version shall stay unlisted.
- If a Krea upload is reserved under a name that has a registered Wan version (or the reverse), then
  `POST .../uploads` shall return 400 and no URL.
- If `--high/--low` is given a Krea file, then the CLI shall refuse before any API call.
- When a `photos` job with `model: krea2` has `loras: "moody:0.8"`, the worker shall load the file as
  one adapter at weight 0.8 into Krea 2, prepend its trigger, and every image shall still be checked
  by the content filter (threshold 0.5).
- When a `video` job with `image_model: krea2`, `avatar: none` has a Wan and a Krea LoRA, the Krea
  LoRA shall apply to the first frame only and the Wan LoRA to the Wan render only.
- If a Krea LoRA is given to a qwen photos job, an avatar job, or a video without `image_model: krea2`,
  then `POST /jobs` shall return 400 naming the LoRA and what it needs.
- If more than 2 Krea LoRAs, a weight outside 0-1.5, or a `step` are given for Krea, then `POST /jobs`
  shall return 400.
- If diffusers can't load an uploaded Krea file, then the job shall fail with "LoRA <adapter> could not
  be loaded: ...".

## Out of Scope

Training Krea LoRAs; Krea LoRA previews; Krea avatar candidates with LoRAs; LoRAs for the Qwen edit
model; Krea LoRA pairs; any change to the content filter or its threshold.

## Risks & Open Questions

- LoRAs trained on Krea 2 Raw may look worse on Turbo (distilled, 8 steps, no CFG). Live check with
  the user's file. (Needs spike: live test.)
- A file can pass the header check but use a layout the converter can't map: the job fails with the
  adapter's name. (Accepted.)
- A LoRA that pushes images toward what the filter flags gets those images dropped, and the job fails
  if all are. Intended: the license (section 4.2) requires the filter. (Resolved.)
- Krea + LoRA VRAM: Krea 2 is ~36 GB on the 48 GB L40S; a few hundred MB of adapters fit, and the
  existing CPU-offload fallback covers the rest. (Resolved.)
- The API's IAM write paths grow by one (`krea2.safetensors`). No feature flag: a single-user tool
  and existing Wan behaviour is unchanged. (Resolved.)

## Testing

Unit (no GPU): kind detection on both header layouts (client and server share it); every refusal at
reserve, register and job submit; routing of mixed lists; `krea.generate` request carries `loras`;
`krea_gen` loads adapters and still filters every image (stub pipeline + stub filter flagging one).
Live: `vidgen lora add <name> --file ~/Movies/lora/kera2_Unlocked_V3.safetensors`, then
`vidgen photos --model krea2 --lora <name> --prompt "..." --count 2`; compare with the same seed
without the LoRA.

## Update: live check (2026-11-23)

- Deployed (API Lambda, API IAM policy, worker code). Uploaded `~/Movies/lora/kera2_Unlocked_V3.safetensors`
  as `kera2-unlocked` (218 MB, 1 min 39 s); registered as `krea2` (512 LoRA tensors).
- Two problems found live and fixed:
  - `peft==0.17.1` (the Wan venv's pin) imports `HybridCache`, removed in transformers 5.x, so every Krea import
    failed once peft was installed (all Krea jobs failed for ~20 min). Pinned `peft==0.21.3`, import-checked on
    the box first.
  - diffusers 0.41 doesn't convert kohya/musubi keys and silently loaded nothing (`set_adapters`: adapter not
    present). Added `kohya_to_reference` (unflatten names, lora_down/up -> lora_A/B, alpha/rank folded into B).
    Checked on the box on CPU against `Krea2Transformer2DModel` (meta device): 256 target modules, 0 missing,
    0 shape mismatches.
- Result: `vidgen photos --model krea2 --lora kera2-unlocked --prompt "a cozy reading corner ..." --count 2
  --seed 42` -> done, 2 images, `loras: [user_kera2_unlocked_v1]`, load 13.1 s, generate 17.0 s, filter 0.07 s,
  0 filtered (threshold 0.5). The same job without `--lora` keeps the composition but differs in details
  (throw, table, window, light), so the adapter is applied.
- Not run live: Krea first frames with a LoRA on video/story (unit-tested only).
